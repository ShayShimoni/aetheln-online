# Structured Observability and Crash Diagnostics

## Purpose and boundaries

Issue [#38](https://github.com/ShayShimoni/aetheln-online/issues/38)
establishes the vendor-neutral prototype contract for structured events,
bounded metrics, and crash context. Observability is a non-authoritative
consumer: a missing context, full sink, failed sink, or unavailable exporter
cannot change validation, damage, cooldowns, movement, rewards, or simulation.

This foundation does not select an exporter, collector, dashboard, alerting
service, or crash-reporting vendor. It also does not establish performance
budgets, a production topology, or a production retention duration.

## Event contract

`aetheln.observability-event` version 1 uses closed enums for the envelope
category, affected subject category, safe reason, internal diagnostic code,
flow kind, metric kind, and environment. The prototype categories are:

- movement, aim, ability, cooldown, hit, dodge, block, resource, death, and
  respawn;
- correction and rejection;
- server lifecycle, server health, and crash context.

Correction and rejection are subject-bearing envelopes: their subject retains
the closed category that was corrected or rejected instead of being silently
rewritten to the envelope category.

Correlation fields are allowlisted and length bounded: flow, run, connection
pseudonym, server instance, activation, ability, and sequence. Build attachment
is separately bounded to source revision, build identity, configuration, engine
revision, and toolchain identity. The existing versioned network profile is
attached without converting an unset measurement into zero or an engine
default.

Before either channel receives an event, the service requires the declared
schema and version, known closed-enum values, nonzero sequence, run/server-
instance/connection correlation, category-appropriate activation and ability
fields, and the matching network-profile schema. Identifier fields reject
C0/C1 control characters and Unicode line/paragraph separators in addition to
their length bounds. A malformed or control-character-bearing record is
dropped from both the public and restricted channels.

The safe reason is suitable for a caller-facing or public record. Restricted
diagnostic codes remain closed and are removed by `MakePublicCopy`. Events do
not accept arbitrary labels, maps, metadata, command bodies, local paths,
credentials, secret keys, account payloads, or character payloads.

## Identity and redaction

- Metrics contain only closed enum dimensions and numeric values. They contain
  no player, character, account, connection, run, ability, or activation text.
- Authoritative runtime code may supply an already pseudonymized connection
  identifier. Client-derived labels and any context without an authority-owned
  pseudonym use the explicit value `excluded`; raw identifiers are never
  transformed into or stored in an event.
- Player-scoped movement and combat producers overlay the server-owned opaque
  connection identifier on each event. The owning client receives that opaque
  value for correction joins; process-wide server health and lifecycle events
  remain explicitly `excluded`.
- When login precedes pawn creation, the GameMode retains the controller-to-
  pseudonym mapping and reapplies it after the normal authoritative restart and
  possession flow.
- Activation identifiers are generated by the authoritative server. A
  pre-activation or otherwise pre-resolution rejection keeps unresolved
  activation and ability fields empty rather than fabricating identifiers.
- Unsupported claim families have schema coverage but must not be reported as
  observed runtime behavior until a real authoritative validation seam exists.
- No credential, personal payload, unrestricted command body, or detection
  detail may be added through a free-form field.

## Runtime ownership and failure behavior

`UAethelnObservabilitySubsystem` owns the service for the lifetime of a game
instance. Producers resolve it at emission time and do not retain sink or
service pointers. Runtime correlation and build/profile contexts are validated
before replacement; invalid replacement leaves the prior valid context intact.

The service has independent public and restricted channels. Authoritative
producers only enqueue into capacity-bounded dispatch queues; sink work runs on
independently scheduled background workers. The public channel has separate
bounded lanes for routine accepted-movement evidence and critical evidence.
The public worker drains critical rejection, correction, and non-routine work
before routine movement, so routine movement saturation cannot consume the
critical lane. A blocked public or restricted sink cannot block the other
channel or authoritative simulation, and saturation drops observability work
rather than waiting or changing gameplay truth. The default public sink
receives only `MakePublicCopy()` and
writes the bounded public contract through Unreal's structured log lifecycle.
The full bounded event is retained separately in a capacity-bounded,
process-local restricted audit buffer; that
buffer never writes diagnostic codes to the ordinary public log. Explicit
injection/reset seams let focused tests or a later access-controlled restricted
exporter replace either channel independently. A later exporter must remain
vendor neutral until a reviewed decision selects it. Public or restricted sink
failure cannot block the other channel, returns no gameplay result, and is
ignored by every producer.

Queue drops and sink-write failures are reported from the background dispatch
workers through a structured warning carrying only the closed channel, failure
kind, work class, delta, and total count. This failure signal bypasses the
saturated telemetry queue and never performs sink I/O on the authoritative
producer thread.

The authority spike configures its context from bounded command-line identities
when the existing scenario is active. Missing packaged provenance remains the
explicit value `unknown`; an unset network profile remains
`network-profile.unset`. A run claiming packaged identity must pass the exact
provenance and profile values already validated by the packaged runner.

## Server lifecycle and crash context

The GameServer module registers engine-supported hooks for:

- first observable game-world tick and server lifecycle startup;
- bounded periodic health snapshots containing monotonic elapsed time from
  world-tick start to world-tick end, total and replicated actor counts, and a
  four-category actor mix of pawn, controller, player-state, and other actors
  without selecting a target or budget. The categories are closed numeric
  metrics and never expose runtime class names;
- controlled world cleanup, with final shutdown emitted as the distinct bounded
  `controlled-shutdown` safe reason rather than a second startup-shaped event;
- pre-registered crash metadata and the engine system-error transition.

Crash-time work is deliberately minimal. Static schema and lifecycle metadata
are registered before failure; the crash callback does not enumerate actors,
serialize gameplay state, perform network I/O, or invoke a provider SDK. This
foundation proves crash-context registration, not delivery of a crash report to
an external service.

### Bounded crash build and correlation context

Issue [#148](https://github.com/ShayShimoni/aetheln-online/issues/148) adds a
closed `FAethelnCrashContextSnapshot` that GameServer's crash-context owner
registers with Unreal's crash context before failure.
`UAethelnObservabilitySubsystem` exposes it through `TryGetCrashContextSnapshot`,
which runs only on the game thread, requires both a runtime and a build/profile
context, returns a validated copy rather than a reference to subsystem state,
and leaves the caller's output unchanged on failure. The snapshot never copies
the caller-supplied run, instance, source, build, toolchain, or profile text
that event correlation uses. It carries only closed sentinels, engine-owned
build values, and a server-generated crash run ID. An invalid runtime, build,
or profile replacement is rejected before it reaches the subsystem, so the
prior accepted context remains the snapshot source; a reset context yields no
snapshot. After every accepted runtime or build/profile change or reset, the
subsystem broadcasts `OnCrashContextChanged` on the game thread; a rejected
change never broadcasts.

Each value is written to an individual, stable `FGenericCrashContext` GameData
key. There is no free-form payload.

| GameData key | Source |
| --- | --- |
| `AethelnObservabilitySchema` | Existing `aetheln.observability-event` schema identity (unchanged). |
| `AethelnServerLifecycle` | Existing lifecycle state (unchanged). |
| `AethelnCrashContextState` | Closed registration state: `missing`, `updating`, `active`, `ambiguous`, or `stale`. |
| `AethelnCrashContextSchemaVersion` | Observability schema version. |
| `AethelnSourceRevision` | Always the literal `unknown`: no in-process verification exists. |
| `AethelnBuildIdentity` | Always the literal `unknown`: no in-process verification exists. |
| `AethelnBuildConfiguration` | Engine-owned `FApp::GetBuildConfiguration`. |
| `AethelnEngineRevision` | Engine-owned `FEngineVersion::Current`. |
| `AethelnToolchainIdentity` | Always the literal `unknown`: no in-process verification exists. |
| `AethelnNetworkProfileSchema` | Network-profile schema identity. |
| `AethelnNetworkProfileVersion` | Network-profile schema version. |
| `AethelnNetworkProfileId` | Always the literal `network-profile.unset`: no in-process verification exists. |
| `AethelnFlowKind` | Closed flow kind, for example `prototype-authority`. |
| `AethelnRunId` | Server-generated opaque crash run ID: 32 lowercase hexadecimal digits from `FGuid::NewGuid`. It is never the launcher run identity. |
| `AethelnServerInstance` | Always the closed server role `game-server`, never a caller-supplied instance identity. |
| `AethelnConnectionPseudonym` | Always the literal `excluded`: crash context is process-wide and never carries a connection identity. |

Design choice: the `AethelnRunId` key name is unchanged, but its value is now
the generated crash run ID rather than the launcher-supplied run. The key set
and count are unchanged. A consumer that expects the launcher run in this key
must use the evidence marker below instead.

Every snapshot value is compared exactly and case-sensitively against its
closed sentinel, engine-owned value, or generated format; a hand-built
snapshot that carries anything else is not bounded, so registration clears it
to `missing`. This check applies at the registration boundary itself, not
only in GameServer's default setup, because any caller can set the subsystem
context. The flow kind must be a known closed value, and the observability and
network-profile schema identity and version must match their constants.
Unset network numerics are never registered. The connection pseudonym must
equal `excluded` exactly; any other value, including a printable
per-connection pseudonym or personal text such as an email address, makes the
snapshot invalid.

The snapshot excludes activation and ability identities, event sequence,
maps, metadata bags, arbitrary labels, paths, raw commands or arguments,
payloads, account or character identities, credentials, and unrestricted
text. The system-error callback never reads the command line.

Generated crash correlation and external provenance are separate:

- External run and build provenance is event correlation only. Unless an
  earlier authority path already set the context, GameServer seeds the event
  run, source revision, build identity, toolchain identity, and
  network-profile identity from the `-AethelnRunId=`,
  `-AethelnSourceRevision=`, `-AethelnBuildIdentity=`,
  `-AethelnToolchainIdentity=`, and `-AethelnProfileId=` launch arguments,
  falling back to `run-local`, `unknown`, and `network-profile.unset`. This
  event behavior is unchanged. The server process cannot verify these
  caller-supplied values; their content trust rests on the launcher. Character validation bounds these values but does not prove they are free of personal or secret text.
  None of them reaches crash GameData.
- Generated crash correlation is server-owned. Every accepted runtime context
  generates a new crash run ID, including a replacement that reuses the same
  launcher run text, so an omitted run that falls back to `run-local` on every
  ordinary launch still registers a distinct ID. A runtime reset clears it,
  and each game instance has its own ID, so a later world or run never
  inherits an earlier one. A build/profile replacement keeps the current ID.
- The `unknown` and `network-profile.unset` crash values are closed sentinels, not verified provenance.
  They state only that the server did not verify source, build, toolchain, or
  profile identity in process. They must not be read as a claim about which
  build ran.

Evidence marker: before registration first becomes `active` with a new crash
run ID, the owner writes one Display line to the server log,
`AethelnCrashContextMarker run=<id>`, carrying only that generated ID. The
line is written during registration on the game thread, never from the
system-error callback. To correlate a crash, match `AethelnRunId` from the
crash report to the marker in the same process's server log, then use that
log's event stream for the launcher-supplied run and build values. The marker
depends on the engine log being enabled for the build; this package does not
change the runner to capture or parse it.

Registration transitions:

- Module startup keeps the existing schema and `module-started` lifecycle keys,
  sets state `missing`, and removes every identity key without claiming a run.
- The first tick of an observable Game or PIE world counts that world before
  its observability subsystem is looked up, configures context when the
  subsystem exists, sets lifecycle `world-running`, and refreshes crash
  context. With exactly one observable world and a valid snapshot, state
  becomes `updating`, all thirteen identity keys are written, and state
  becomes `active`.
- An accepted runtime or build/profile change or reset on the sole tracked
  world's game instance refreshes crash context immediately, without waiting
  for another world tick. A valid replacement follows the same
  `updating`-to-`active` sequence and overwrites every identity key; an
  accepted runtime replacement registers a newly generated crash run ID, so
  no prior crash run remains. A reset sets `missing`. A
  rejected replacement changes nothing, so the last valid registration stays
  `active`.
- A missing or invalid snapshot sets state `missing` and removes every
  identity key. It never partially overwrites a valid registration. A sole
  observable world without an observability subsystem is `missing`.
- When more than one observable world is tracked, including a world without an
  observability subsystem, state becomes `ambiguous` and every identity key is
  removed. Context changes are ignored while ambiguous. The server never
  selects one world.
- World cleanup and module shutdown set state `stale` and remove every identity
  key. Lifecycle transitions remain `world-running` or `controlled-shutdown`
  after cleanup, and `module-stopped` at shutdown.
- A later tick from a single remaining observable world replaces `stale` or
  `ambiguous` context through the same `updating`-to-`active` sequence. A
  refresh that yields `missing` is not retried every tick.
- The engine system-error callback only changes lifecycle to `crashing`. It
  does not inspect worlds or actors, query the subsystem, serialize gameplay,
  read the command line, allocate an unbounded payload, perform sink,
  provider, network, or file I/O, wait on telemetry, or alter gameplay truth.

The state key is written before identity keys are removed and after they are
written, so an interrupted update never reads as `active`. The owner removes
only its owned keys with `FGenericCrashContext::SetGameData(Key, TEXT(""))` and
never calls `FGenericCrashContext::ResetGameData`. A destroyed world that was
never cleaned up still counts as tracked, so the process stays `ambiguous`
rather than risking cross-world attribution.

Limitations of this package:

- No CrashReportClient, uploader, vendor, endpoint, or external submission is configured.
- This package proves registration behavior only. It does not run or claim an
  actual controlled crash.
- Local-only report generation, a safe trigger, allowlisted text extraction,
  and a real controlled packaged Linux server crash remain deferred.
- Raw core and minidump files must never be opened, parsed, hashed, copied, or published.
- Crash-report retention remains `TBD`.

## Environment and retention boundary

| Environment | Destination and access | Retention |
| --- | --- | --- |
| `local` | Bounded public events and closed metrics use the ordinary Unreal log lifecycle. The contributor controls local access; no shared endpoint exists. | Unreal log rotation is operational behavior, not an approved policy. Exported local evidence retention is `TBD`. |
| `development` | Packaged client/server logs record the same bounded public contract. A future access-controlled collector may consume the sink interface after a reviewed decision. | `TBD`; no duration is approved by this issue. |

Environment is not inferred from Unreal's build configuration. The closed
`AethelnEnvironment` runtime input defaults ordinary contributor execution to
`local`; the packaged multiplayer evidence runner requires and propagates
`development`. Unsupported values suppress metric emission rather than being
silently relabeled, and they cannot change authoritative gameplay outcomes.

The default structured-log sink strips restricted diagnostic codes and escapes
validated identifiers before output. Tests may inject the bounded in-memory or
explicit no-op sink. No external vendor, endpoint, or credential is selected.
The default process-local restricted audit buffer lasts only for the game
instance lifetime and is not a policy retention duration or an authority
store. It is not exposed through gameplay endpoints or the public log. Any
external persistence, investigation access role, integrity control, or export
retention remains `TBD` and requires the separately reviewed restricted
operations integration.

`QA` remains a board status, not an environment. `staging` and `production` are
not created by this prototype contract. Production retention, privacy
jurisdictions, RPO/RTO, exporter credentials, deletion handling, and access
roles remain `TBD` under the owning architecture and operations decisions.

## Verification and downstream ownership

Focused Unreal automation covers schema/version stability, bounded correlation,
build/profile attachment, public/internal separation, sink capacity and
failure, GameInstance ownership, authority outcome invariance, representative
rejection families, server health metrics, crash-context keys, the closed
crash-context snapshot, registration state transitions, immediate refresh after
accepted context changes, multi-world ambiguity including worlds without a
subsystem, the excluded process pseudonym, exclusion of printable personal or
credential-like launcher text from every crash GameData key, generated crash
run rotation across omitted-run launches and world or runtime replacement, and
the lifecycle-only system-error handler. The evidence-marker test expects a
Display log line; that capture path has not yet run natively.

Crash-context ownership (`FAethelnCrashContextOwner`: the fourteen crash-context
keys, the closed states, observable-world counting, and accepted-change
refresh) lives in GameNet, which both `AethelnOnlineEditor.Target.cs` and
`AethelnOnlineServer.Target.cs` list. Its `Aetheln.Observability.CrashContext.*`
tests create their own owner and worlds rather than broadcasting to the loaded
GameServer module, so a server's own map world cannot make them ambiguous; they
declare `EditorContext | ServerContext`. GameServer keeps only the lifecycle
keys, context seeding, and the system-error handler; its
`Aetheln.Observability.Server.SystemErrorLifecycleOnly` test declares
`EditorContext | ServerContext`.

For a claim family whose gameplay system is not yet implemented, the opt-in
packaged authority scenario provides a server-authoritative, fail-closed
rejection entry point. It cannot accept the claim or mutate gameplay, and it
emits the same bounded public envelope as an implemented validation path. When
that gameplay system is introduced, its real authoritative validator becomes
the required producer and the scenario probe remains provisional, supplemental
evidence rather than observation of production gameplay behavior.
