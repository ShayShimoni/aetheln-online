## AC1: Enhanced Input inventory

### Ownership and lifecycle

- **No input assets.** No `IA_*` or `IMC_*` asset exists under `Content/`. Every action and the single mapping context are transient objects created in code by `InitializeActions` (`AethelnPOCInputComponent.cpp:228-303`). `DefaultInput.ini` only selects `EnhancedPlayerInput` and `EnhancedInputComponent` as the default classes; there is no Enhanced Input user-settings or player-mappable-key configuration.
- **Owner.** `UAethelnPOCInputComponent` (`GameUI`, `UCLASS(Transient)`, `AethelnPOCInputComponent.h:20-25`) owns all actions, the context, the overlay widget, viewport capture, and Reticle/Cursor mode. The `BP_MovementPOCCharacter` asset (a thin `AAethelnPlayerCharacter` Blueprint) selects it through `OverrideInputComponentClass`, and `BP_MovementPOCGameMode` uses that Blueprint as its default pawn; the `MovementPOC` map uses that game mode. These asset facts were read from the assets' serialized names, not by opening the editor. The engine creates the override input component when the pawn restarts under a local player controller and destroys it on unpossession.
- **Binding.** `BindReceiver` binds only when the owner pawn has a local `APlayerController` and implements `IAethelnPlayerInputReceiver` (`AethelnPOCInputComponent.cpp:305-353`). The receiver interface (`AethelnPlayerInputReceiver.h:23-31`) has move, look, zoom, aim-steering, jump started/stopped/canceled, sprint, and dodge-pressed (`ReceiveDodgePressed`, `:31`) methods only; it has no attack, defense, or ability method. `AAethelnPlayerCharacter` implements the dodge method (`AethelnPlayerCharacter.h:36`, `AethelnPlayerCharacter.cpp:826-832`), which calls `RequestDodge` on the locally controlled pawn only. Nothing in `GameUI` calls it yet, because `IMC_POC_Movement` has no dodge action.
- **Add.** `ActivateLocalPlayerResources` adds `IMC_POC_Movement` to the local player's `UEnhancedInputLocalPlayerSubsystem` at **priority 0** with `bIgnoreAllPressedKeysUntilRelease = true` (`AethelnPOCInputComponent.cpp:69-74`, `:368-380`). It runs from `OnRegister` (`:186`) and `ApplicationHasReactivated` (`:453-457`). A `bContextApplied` guard prevents a duplicate add.
- **Remove.** `ReleaseLocalPlayerResources` removes that exact context (`:410-417`) and the overlay widget (`:421-425`) after forcing Cursor mode (`:398`). It runs from `OnUnregister` (`:189-194`), `OnComponentDestroyed` (`:196-205`, which also clears bindings), and `ApplicationWillDeactivate` (`:448-451`). Reactivation restores the context in Cursor mode, so focus recovery does not silently recapture.
- **Packaged authority pawn.** `AAethelnNetworkSpikeGameMode` uses the C++ `AAethelnSpikeCharacter` as its default pawn class (`AethelnNetworkSpikeGameMode.cpp:30`). It sets no override input component, so it gets the default Enhanced Input component with no mapping context: the packaged spike has **no player input at all**. Its only movement is a scripted `AddMovementInput` (`AethelnSpikeCharacter.cpp:60-63`) and its only attack is a timed programmatic `SubmitFreeAimAttack(GetActorForwardVector())` (`:76-80`). That aim is the actor's forward vector, which is not guaranteed to equal the control-rotation vector the server compares it with; see the packaged-pawn prediction under [Findings](#findings) (F1). `AAethelnSpikeCharacter` derives from `AAethelnPlayerCharacter` (`AethelnSpikeCharacter.h:11`), which implements the input receiver (`AethelnPlayerCharacter.h:17-20`), and it uses a movement component derived from the project one (`AethelnSpikeCharacter.cpp:30`, `AethelnSpikeMovementComponent.h:9`). The integration owner can therefore reuse the existing receiver and saved-move flags on this pawn.

### Active actions in `IMC_POC_Movement`

No mapping has an explicit trigger object, so Enhanced Input's implicit default (down) trigger behavior applies to every mapping. The only modifier in the project is `UInputModifierNegate` on the look Y axis. No gamepad, touch, or alternative key is mapped.

With no trigger objects, an action only moves between Triggered and None (`Engine/Plugins/EnhancedInput/Source/EnhancedInput/Private/EnhancedPlayerInput.cpp:241`, `:689`), and Canceled is raised only when an action leaves Ongoing (`:120-176`). So the Canceled bindings for move, jump, and sprint below cannot fire today. The jump-buffer clear on cancel runs only through Cursor entry (`AethelnPOCInputComponent.cpp:435`). Owners must not rely on a Canceled event until a trigger exists.

## AC2: Camera and aim independent of presentation and collision

No race, sex, body, or appearance concept exists in `Source/` gameplay code. A case-insensitive whole-word search for race, sex, gender, appearance, female, and male finds only the comment at `AethelnCombatCollision.h:10`, which states that capsule responses are set the same way for every race, sex, and appearance. No code branches on any of them, so no such value can reach camera, aim, or collision code today. The positive evidence is:

| Property | Evidence |
| --- | --- |
| Authoritative capsule is fixed in C++, not taken from the mesh | `AethelnPlayerCharacter.cpp:676` |
| Body never copies controller rotation directly; facing is a movement-simulation decision | `AethelnPlayerCharacter.cpp:680-682`; `AethelnCharacterMovementComponent.cpp:500-553` |
| Camera boom attaches to the capsule root and follows control rotation; the camera adds no rotation | `AethelnPlayerCharacter.cpp:698-710` |
| Zoom, shoulder offset, target height, and mesh hiding run only on the locally controlled client and change only boom offsets and owner-only mesh visibility | `AethelnPlayerCharacter.cpp:727-736`, `:912-949` |
| Dedicated server disables pawn tick, so per-frame presentation code does not run there. Event-driven mesh writes still run on the server and touch only the mesh. | `AethelnPlayerCharacter.cpp:721-724`; `:834-876` |
| Presentation yaw rotates only the mesh, locally | `AethelnPlayerCharacter.cpp:1004-1029` |
| Spring-arm collision probing moves only the camera, not the capsule | `AethelnPlayerCharacter.cpp:703` |
| Movement direction comes from control yaw, not the camera or mesh | `AethelnPlayerCharacter.cpp:951-957` |
| Backpedal, speed caps, and facing are judged from move acceleration and control yaw | `AethelnCharacterMovementComponent.cpp:391-434`, `:514-553` |
| Server aim comes from controller control rotation | `AethelnSpikeAuthorityComponent.cpp:385-391` |
| Attack origin is the actor (capsule) location plus aim; the query shape is a server-side value | `AethelnSpikeAuthorityComponent.cpp:530-539` |

Limits of this evidence:

- Only one presentation variant (`SKM_Quinn_Simple`) exists, so the male/female equivalence test required by [Automation and Manual Validation](combat-and-networking-architecture.md#automation-and-manual-validation) cannot run yet.
- This evidence covers the attacker. The attack query matches every dynamic object type (`AethelnSpikeAuthorityComponent.cpp:533-539`), and the engine's default `CharacterMesh` profile is query-enabled with object type Pawn (`Engine/Config/BaseEngine.ini:3112`), which `ACharacter` applies to its mesh (`Engine/Source/Runtime/Engine/Private/Character.cpp:130-131`). No `Source/` C++ overrides it; Blueprint assets were not inspected. The spike enemy is sphere-only (`AethelnSpikeEnemy.cpp:12-17`), so the spike query has nothing wrong yet. The activation-seam path (#60) resolves contact differently: it sweeps the dedicated `AethelnCombatQuery` channel (`Config/DefaultEngine.ini:25`, `AethelnCombatCollision.h:5-13`, `AethelnCombatTimelineSubsystem.cpp:287`), where the player capsule and the capsule-based `AAethelnCombatAICharacter` respond with Overlap and meshes keep the channel's Ignore default (`AethelnPlayerCharacter.cpp:677-678`, `AethelnCombatAICharacter.cpp:16`), pinned by `Aetheln.GameCombat.AttackTimeline.ContactOnCapsuleOnly` (`AethelnAttackContactTests.cpp:51`). Only the spike query, which matches every dynamic object type, could let a mesh decide a hit once players become its targets.
- The reticle is a fixed screen-center glyph (`AethelnPOCOverlayWidget.cpp:63-64`), so it marks the camera's forward ray. The server attack ray starts at the capsule and is parallel to it, offset by arm length, target height, and shoulder offset. Near cover can block one ray and not the other. This is a readability question for phase 2, not an authority defect.

**F1 note: engine mechanism (UE 5.8.1 source, code reading only).** This is the mechanism behind the original spike-request finding; the activation seam bounds the difference instead of requiring equality (F1 row). The client may hold a new move as `PendingMove` and send nothing when the last send was less than one move-send interval ago (`Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp:9034-9047`). `FSavedMove_Character::CanCombineWith` compares no control rotation (`:13085-13266`), so a held move can absorb later look motion. The server applies control rotation only inside `ServerMove_PerformMovement`, after the timestamp check (`:9995`) and only for a positive move delta (`:10027-10036`). A lost, expired, or zero-delta move leaves it unchanged. The movement RPC is unreliable (`Engine/Source/Runtime/Engine/Classes/GameFramework/Character.h:376-377`) and its payload carries the saved control rotation (`Engine/Source/Runtime/Engine/Private/Components/CharacterMovementComponent.cpp:9802`), while the reliable `ServerSubmitAttack` is sent in the next packet whatever the move state, and a retransmitted intent can arrive after newer moves moved the rotation on. At the press, the server therefore holds the rotation from the last move it processed, which can be one send interval old or older. Quantization is not the cause. Both the aim normal and the packed control rotation keep far finer precision than the tolerance. The size of the effect is a prediction until phase 2 measures it (S5).

**F1 note: packaged-pawn prediction (code reading, unmeasured).** The packaged attack's aim equals the control-rotation vector only while the body faces control yaw, and the inherited facing rules do not guarantee that after the scripted strafe. `AAethelnSpikeCharacter` inherits `bUseControllerRotationYaw = false` (`AethelnPlayerCharacter.cpp:680-682`) and the movement-decided facing described in the AC2 table (`AethelnCharacterMovementComponent.cpp:500-553`). The scripted half-second strafe adds input along the actor's own right vector (`AethelnSpikeCharacter.cpp:60-63`). With no aim steering, orient-to-movement turns the body toward that vector. Once the body has turned a little, `IsBackpedaling` (`AethelnCharacterMovementComponent.cpp:416-421`, with a near-zero dot tolerance) selects camera facing and turns the body back. Reading the code predicts that the facing alternates, so where it ends is not guaranteed. The attack then submits `GetActorForwardVector()` (`AethelnSpikeCharacter.cpp:76-80`) and the server compares it with the unchanged control rotation (`AethelnSpikeAuthorityComponent.cpp:268-273`, `:385-391`). A packaged run may therefore itself record `impossible-aim-transition`. This is a phase 1 prediction handed to #2. A packaged capture now exists: the package built at [#129](https://github.com/ShayShimoni/aetheln-online/pull/129) head `9c960497` (merged as `74bd706a`; run 31952847659 is the post-merge quality-gates run) recorded one Linux server and two Windows clients under neutral present-time conditions only, with no measured network values; the full record is in [Networking Authority Spike](networking-authority-spike.md), added by [#317](https://github.com/ShayShimoni/aetheln-online/pull/317). This document does not read that capture for the predicted rejection, so the prediction is not settled here.

### Integration rules

- `GameUI` owns local actions, mapping-context installation, viewport capture, Reticle/Cursor state, and non-authoritative feedback. `GameCore` receives movement, look, zoom, jump, and sprint intent through the presentation-neutral receiver. `GameCombat` owns server-validated ability requests and outcomes; it must not import `GameUI` or let UI or animation decide hits.
- Install one owned mapping context per local player and possession, and remove that exact context when its owner is unpossessed, unregistered, destroyed, leaves the local player during travel, or loses focus. A later integration may disable instead of remove on focus loss, but must enter Cursor mode, block new gameplay input, clear pending local state, restore idempotently, ignore keys held across restoration, suppress the first recaptured mouse delta, and consume the recapture click.
- Cursor mode blocks new move, look, zoom, jump, sprint, dodge, attack, defense, and ability presses and sends release or cancel where needed. It does not erase momentum, cancel an accepted server activation, or pause an authoritative timeline. Future CommonUI and dialogue layers use stacked cursor ownership. A UI-handled click never recaptures.
- Candidate actions are not approved mappings. The product approves remappable LMB primary attack, remappable RMB class defense, and Space jump. The dodge default, one remappable Left Ctrl key, was owner-approved on 2026-10-10 ([Dodge and Block](dodge-and-block.md), decision 10, `docs/dodge-and-block.md:991`). Ability keys, controller layout, chord behavior, remap UI, and accessibility targets remain unselected. Do not steal Space for a combo follow-up or treat the Cursor-mode recapture click as an attack.
- Integrated automation exercises fresh and canceled presses across Reticle/Cursor, focus, possession, death/respawn, and reconnect, and proves that stale, duplicate, version, aim, time, and availability rejections leave no duplicate side effect.
- Camera, aim, and movement stay independent of race, sex, body preset, appearance, and visual scale. Every presentation variant uses one authoritative capsule, one set of movement and combat rules, and one aim semantics. Reticle placement, shoulder parallax, close-camera mesh hiding, animation offsets, and presentation sockets never change authority. Verify near-cover obstruction separately before claiming reticle and attack alignment.
- Numeric timing, aim, rate, and resource bounds remain `TBD` for their evidence owners. A provisional code value is not its approval.
